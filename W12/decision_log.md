## 欄位語意與後續用途 － 對應評分：context_clarification

## 清洗規則 － 對應評分：de_rules

| 欄位 | 處理方式（保留／轉換／補值／設 NULL／排除／隔離） | 理由 |
|---|---|---|
| （整列重複） | 排除（保留第一筆） | Claire 說是同一批資料匯出兩次，不是兩個不同的申請；留著會讓同一個申請案在 EDA 和建模被算兩次 |
| ID | 空白的整列隔離，另存 credit-quarantine.csv；其他保留原值不動 | Alex 說上線後要用 ID 跟還款紀錄對帳，ID 必須唯一不變；空白的 ID 是匯出時遺失，沒辦法對帳，也不能自己編號。隔離而不是直接丟，是因為 Claire 說這些申請是真的，之後如果找回編號還可以補回來 |
| AGE | -1、unknown、空白 → 設 NULL；轉成整數 | Claire 說 -1 是系統預設值、unknown 是字跡看不清楚，兩種都不是真的年齡；如果留著 -1 會被當成真的數字，補平均值又等於自己編年齡 |
| MARITAL_STATUS | ??、NULL → 設 NULL；其他統一小寫 | Claire 說是申請人拒答；規格只允許三個類別，拒答不能硬歸到任何一類 |
| PAY_0 | late → 設 NULL；其他轉成整數 | late 只知道有逾期、不知道幾個月，補成任何月數都是自己編的（Ethan 也提醒會拉近或拉遠真實月數）；整列排除又會少掉 31 個真的有逾期的案例。設 NULL 後 missing_rate 是 16.32%，仍在 20% 以下 |
| BILL_AMT1 | 空白 → 補 0；n/a → 設 NULL；轉成整數 | Claire 說空白是新戶還沒出帳、真的沒有帳單，所以 0 就是正確的金額；n/a 是同步失敗、金額存在但不知道，補 0 會把有帳單的人變成沒帳單，所以只能設 NULL |
| signup_at | 全部轉成 ISO-8601 UTC（`YYYY-MM-DDTHH:MM:SSZ`）；not-a-date → 設 NULL | 規格要求 ISO-8601 UTC。`2024/01/02 18:00+08:00` 換算成 UTC 是 10:00；`01/02/2024` 依 Claire 說明是 1 月 2 日台北時間，沒有時分，所以當成台北時間 00:00，轉成 UTC 是 2024-01-01T16:00:00Z；not-a-date 是欄位損毀、時間救不回來 |
| default | 保留，只檢查型別和範圍 | 這是模型要預測的答案，不能改也不能補 |
| LEAK_FUTURE_DEFAULT | 保留原值，不改動；在紀錄中標註「建模不得使用」 | Claire 說是結果期之後才回填的，申請當下拿不到，而且每一列都跟 default 一樣，拿來建模就是資料洩漏；但 QA 規定不能整欄刪掉，所以保留欄位、交代 W14 選特徵時一定要排除 |
